**Helm chart를 바꾸면 실제로 뭐가 달라질까? 그래서 Diffaro를 만들었다**

Helm chart를 수정하다 보면 항상 궁금했다.

그래서 이걸 적용하면 실제로 뭐가 바뀌는가?

Git diff를 보면 어떤 파일과 값이 바뀌었는지는 보인다. 하지만 그 값이 Kubernetes에 적용될 리소스를 어떻게 바꾸는지까지 바로 알기는 어려웠다.

그래서 `helm template`을 실행하거나, 파일을 읽고 머릿속으로 추적하는 경우가 많았다.

문제는 내가 App of Apps 구조를 사용하고 있었다는 것.

부모 App을 보고, 하위 App을 보고, 거기에 들어가는 values와 parameter까지 찾아야 했다. 하위 App이 다시 다른 App을 만들면 또 따라가야 한다.

→ 부모 App의 렌더링 결과 확인  
→ 하위 App의 설정 확인  
→ 하위 App을 다시 렌더링  
→ 그 안에 App이 있으면 반복

말로 쓰면 간단하다.

그런데 실제로 하려면 `helm template` 명령어를 만드는 것부터 버거웠다. 어떤 values 파일을 쓰는지, parameter는 무엇인지, 어떤 namespace로 들어가는지 찾아서 입력해야 한다.

한 번 확인하고 끝나는 것도 아니다. chart를 수정할 때마다 다시 해야 한다.

수정이 많아질수록 확인해야 하는 것도 많아지고, 점점 피곤해졌다.

App of Apps는 DevOps 엔지니어조차 전체 구조를 파악하기 어려운 경우가 있다. 그런데 변경할 때마다 이걸 사람이 머릿속으로 따라가야 하나 싶었다.

이 과정은 도구가 해야 한다고 생각했다.

내가 원했던 것은 PR을 올렸을 때, 변경 전후를 비교해서 실제 리소스가 어떻게 달라지는지 보는 것이었다.

어떤 Application이 생기는지, 어떤 리소스가 바뀌는지, 무엇이 사라지는지.

누가 이미 만들었을 것 같았다. 나만 겪는 문제는 아닐 테니까.

하지만 내가 찾던 도구를 찾지 못했다.

그래서 직접 만들기 시작했다. 그게 Diffaro다.

앞으로 AI를 이용해서 Helm chart나 values를 수정하는 일도 더 많아질 것이라고 생각했다.

수정하는 속도는 빨라질 것이다. 그러면 그 결과를 확인하는 과정도 따라가야 한다.

AI가 바꿔준 파일을 사람이 읽고, 렌더링 결과를 머릿속으로 예상하고, 하위 App까지 추적한다면 확인하는 부담은 여전히 남는다.

PR에서 실제 리소스의 변화를 볼 수 있으면 좋겠다고 생각한 이유다.

Diffaro의 기본 흐름은 다음과 같다.

```text
GitHub PR 또는 base/head revision 입력
    → 비교할 commit SHA 확정
    → 각 revision을 Argo CD backend로 렌더링
    → Application 구조와 Kubernetes 리소스 비교
    → Markdown / JSON 보고서 생성
```

GitHub PR을 입력하면 merge-base와 head를 비교한다.

merge-base는 PR 브랜치와 대상 브랜치의 공통 조상이다. 이 시점과 PR의 head를 commit SHA로 확정해서 비교한다.

그러면 어떤 revision을 기준으로 나온 결과인지 확인할 수 있다.

그다음은 렌더링이다.

여기서 Application의 설정을 제대로 사용하는 것이 중요하다.

Helm chart는 같은 chart라도 어떤 입력을 넣는지에 따라 결과가 달라진다.

- `valueFiles`
- inline `values`와 `valuesObject`
- `parameters`와 `fileParameters`
- `releaseName`
- destination과 namespace
- Kubernetes 버전과 API capabilities

내가 `helm template`을 실행할 때 직접 찾아 넣어야 했던 것들이다.

입력이 빠지거나 달라지면 렌더링 결과도 달라질 수 있다. 그래서 Diffaro는 설정된 Argo CD backend를 통해 양쪽 revision을 렌더링한다.

기존 Application의 설정을 유지하고 revision만 바꾸는 경우에는 Application manifest API를 사용한다.

하지만 부모가 새로운 child Application을 만들거나 child의 values 설정, parameters, destination 등을 바꾸면 이야기가 달라진다. 저장된 Application의 현재 설정으로 렌더링해서는 변경된 child의 결과를 확인할 수 없다.

이 경우에는 해당 설정을 렌더링할 수 있는 repo-server backend와 렌더 context가 필요하다.

여기가 렌더링을 구현하면서 복잡해지는 부분이다. 필요한 설정과 권한을 연결해야 하고, 처리할 수 없는 경우도 명확하게 보여줘야 한다.

렌더링하지 못했는데 변경이 없다고 나오면 안 된다.

App of Apps는 재귀적으로 추적한다.

부모 App을 렌더링하면 결과 안에 하위 `Application` 리소스가 있을 수 있다. 그 Application의 spec을 읽고 다시 렌더링한다.

그 안에 또 Application이 있으면 같은 과정을 반복한다.

```text
Root Application
    → 하위 Application
        → 하위 Application
            → Kubernetes 리소스
```

내가 사용하던 구조를 생각하면 이 방식이 가장 자연스러웠다.

다만 한쪽 구조만 따라가면 충분하지 않다. PR의 변경으로 child가 추가되거나 없어질 수도 있기 때문이다.

그래서 base와 head를 각각 렌더링하고, 각각의 Application 그래프를 만든다. 그 후 Application 관계와 최종 리소스를 비교한다.

여기서 비교 기준은 양쪽 revision의 target manifest다.

현재 클러스터에 떠 있는 리소스와 PR을 비교하는 방식은 아니다. PR의 변경 전후가 각각 어떤 리소스를 만들 것인지 확인하는 것이다.

확인하기 위해 실제 배포를 하거나 운영 Application을 수정하지도 않는다.

재귀 탐색을 구현하면서 걱정됐던 것은 규모였다.

App이 몇 개일 때는 괜찮을 수 있다. 그런데 깊게 nested되어 있거나 App이 많으면 어떨까?

App을 하나 찾는 것으로 끝나지 않는다. 그 App을 렌더링해야 하고, 결과를 읽어야 하고, 다시 하위 App을 찾아야 한다. 이걸 base와 head에서 각각 해야 한다.

탐색과 렌더링 비용이 커질 것 같았다.

현재는 최대 깊이, Application 수, timeout 같은 제한을 두고 순환 관계를 검사한다. 같은 Application을 여러 경로에서 발견하는 경우도 처리한다.

그렇다고 큰 구조에서의 성능 고민까지 끝난 것은 아니다. 어떤 규모에서 시간이 얼마나 걸리고, 어디에서 비용이 커지는지는 계속 확인해야 한다.

다양한 유스케이스를 어디까지 커버할 수 있을지도 마음에 걸렸다.

내가 사용하는 환경에서 동작한다고 다른 사람의 환경에서도 충분하다고 할 수는 없다. 저장소 구성도 다르고, values를 관리하는 방법도 다르고, Application 구조도 다를 것이다.

현재는 Git 저장소의 Helm source를 중심으로 지원 범위를 두고 있다. 모든 Argo CD source와 모든 구성 방식을 지원하는 도구는 아니다.

실패한 경우를 어떻게 보여줄지도 중요했다.

어떤 branch를 탐색하지 못했다고 해서 그 안의 Application이 삭제됐다고 판단하면 안 된다. 확인하지 못한 것과 실제로 없는 것은 다르다.

또 하나의 branch가 실패했다고 정상적으로 비교한 다른 결과까지 사라지면 곤란하다.

그래서 성공한 결과는 남기고, 실패한 지점과 확인하지 못한 범위를 같이 보여준다.

GitHub 연동, 렌더링, 재귀 탐색, 비교까지 연결하다 보니 생각보다 고려할 것이 많았다. 필요한 기능을 넣으면서도 너무 복잡해지지 않도록 고민했다.

그러다 중첩된 App of Apps 구조의 diff를 잡아낸 순간이 있었다.

테스트용으로 만든 구조였다. 하지만 바탕은 실제로 사용하던 구조였다.

평소 머릿속으로 따라가야 했던 관계를 테스트 환경에 재현하고, 그 안에서 변경 전후의 차이를 확인했다.

그때 쓸만은 하다고 느꼈다.

모든 유스케이스를 커버할 수 있다는 확신이 생긴 것은 아니었다. 그래도 내가 버거워했던 작업을 도구가 대신할 수 있겠다는 생각은 들었다.

현재 Diffaro는 리소스 비교를 기반으로 몇 가지 운영 영향도 분석한다.

- Service selector에 매칭되던 Deployment의 Pod template이 head에서 모두 사라지는 변화
- Deployment 롤링 업데이트 설정의 계산상 최소 가용 수가 양수에서 0으로 바뀌는 조건
- 변경된 ConfigMap을 참조하는 Deployment의 범위

여기에도 확인할 수 있는 범위가 있다.

Service의 매칭 대상이 사라지는 설정을 발견했다고 실제 트래픽 장애가 발생했다고 말할 수는 없다. ConfigMap을 참조한다고 프로세스가 자동으로 reload되거나 반드시 재시작한다고 말할 수도 없다.

렌더링된 리소스에서 확인한 사실과, 추가로 확인해야 하는 조건을 같이 보여줘야 한다.

Diffaro의 비교와 영향 분석에는 LLM을 사용하지 않는다. 렌더링 결과와 정해진 규칙을 근거로 결과를 만든다.

오픈소스로 만드는 이유는 누구나 사용할 수 있었으면 하기 때문이다.

누군가 이미 만들었을 것 같아서 찾았던 도구를 내가 만들게 됐다. 같은 문제를 겪는 다른 사람은 이 도구를 이용할 수 있으면 좋겠다.

그리고 피드백을 받고 싶다.

내가 사용하던 구조만으로는 놓치는 부분이 있을 것이다. 다른 환경에서 사용해 보면 예상하지 못한 문제도 나올 것이고, 필요한 기능도 더 구체적으로 알 수 있을 것이다.

지원 범위와 성능은 지금도 고민 중이다.

그래도 중첩된 App of Apps의 diff를 확인했던 순간, 계속 만들어 볼 이유는 생겼다.

다른 사람도 써보고 쓸만하다고 느끼면 좋겠다. 부족한 부분은 피드백을 받으면서 발전시켜 보고 싶다.
